Mental Model

Signal Forms are a third way to build forms in Angular, alongside template-driven and reactive forms. They replace the imperative control objects of Reactive Forms with a reactive, declarative model built directly on Angular Signals.

What is a Signal Form?

A Signal Form is a field tree wrapped around an ordinary model signal. Your data lives in a WritableSignal; the form mirrors that shape as a tree of callable field accessors; a declarative schema attaches validation and behavior to each field; and the [formField] directive binds those fields to DOM controls.

Why Angular introduced them

Reactive Forms solved the "big application" problem of template-driven forms — typed control trees, validation, fine-grained state — but with real costs:

  • Two copies of the data. A FormGroup duplicates your model, and you spend your life syncing them with setValue/patchValue.
  • Imperative glue. Conditional validation, cross-field rules and disabled logic are assembled with valueChanges subscriptions and updateValueAndValidity calls scattered through components.
  • Subscription tax. Every read is a stream; every derived value needs a subscription, an unsubscribe, and a hand-rolled state update.
  • Weak typing. AbstractControl-based access hides the data shape behind casts; strong typing for reactive forms shipped late and still lives mainly in FormControl<T> boilerplate.

What actually changes conceptually

The mental model shifts in four ways:

Reactive FormsSignal FormsWhy it matters
FormControl field accessor → field() State is read as a signal, not an object to subscribe to.
FormGroup / FormArray the field tree over the model No duplicate data — one model signal is the source of truth.
valueChanges / statusChanges field().value(), computed(), effect() Derivation is declarative and glitch-free; no subscriptions to manage.
validators: [...] on controls schema rules: required(path), validate(path, fn) Rules are declarative, composable and reusable across forms.
setValue() / patchValue() model.set() / model.update() (or field().value.set()) Updating the data updates the form; updating the form updates the data.
Validators.required etc. required, email, min, minLength… Built-in validators are standalone schema rules with user-facing messages.

How form state is represented

Every node of the field tree is a callable accessor. Calling it returns a FieldState — a snapshot of that field's reactive state: value, touched, dirty, valid, invalid, pending, errors, and more. The root field aggregates its descendants, so form().valid() folds the whole tree up.

What becomes simpler

  • Data sync — the form is the model signal; nothing to keep in step.
  • Typed access — form.personal.firstName is typed end to end.
  • Reactive reads — computed() over fields, no subscriptions.
  • Declarative rules — validation, disabled, readonly, hidden as schema.
  • Async validation — debounced and pending-aware out of the box.
  • Submission — server errors map back onto fields directly.

What does NOT become simpler

  • Architecture — you still need to decide where the model lives and who owns it.
  • Large-form layout — splitting templates into section components is still on you.
  • Third-party control ecosystems — most Angular UI libraries still speak ControlValueAccessor; Signal Forms interoperate, but some controls need a wrapper.
  • Migration — converting a large reactive form is a rewrite of logic, not a find/replace.
When Signal Forms are appropriate: most new forms, complex validation, dynamic/nested data, API-backed editors, anything you'd reach for Reactive Forms for.
When Reactive Forms may still be better: legacy codebases fully invested in the Reactive Forms ecosystem, teams migrating a stable form they never touch, or strict requirements for AbstractControl interop with third-party controls.

First Signal Form

We'll build a small User Profile Form — name, email, age — step by step. This is the same code running live below, so experiment with it: try submitting empty, then fill it in and watch every state signal update.

Step 1 — The form model

Start with an interface and one writable signal. There is no FormGroup; the signal is the data. This is the whole point — the form adds behavior, not a second copy of the state.

Why it works: form() reads the shape of the model signal and builds a field tree that mirrors it. When the signal changes, the tree follows.

Step 2 — Signal-based form state

Wrap the model with form(model, schemaFn). The second argument is a schema function that declares rules — here, validation — per field using paths into the model shape.

What is reactive: every rule is registered as a reactive dependency on the field's value. Nothing is computed until you read it; nothing is recomputed unless its inputs changed.

Step 3 — Field bindings

The [formField] directive binds a field to a DOM control: it pushes value changes into the field, pushes field state back into the DOM, and marks the field touched on blur. The [formRoot] directive wires the <form> element to submission and disables native browser validation.

What Angular is doing: for a native <input> the directive attaches an input listener and a renderer-driven write-back — no ControlValueAccessor needed, no two-way binding boilerplate.

Step 4 — Reading values

Notice the pattern: a field is called to reach its state, and state properties are signals that you call to read. This consistency is what makes computed() and templates Just Work.

Step 5 — Updating values

Why it works: the field's value is a writable signal that writes back into the model. Bulk replacement goes straight to the model — the tree re-wraps the new object. Both routes keep validation, dirty and touched in sync.

Step 6 — Validation

Validation is declared in the schema, not assembled in the component. Each rule can carry a user-facing message — so the template renders err.message directly and you never translate error codes in the UI.

Step 7 — Error display

Errors are per-field signals. The same errors() list drives aria-invalid, aria-describedby and the visible message — one source of truth for both screen readers and sighted users.

Step 8 — Submission

Submission is declared once, in the form options. [formRoot] intercepts the native submit event, marks the whole tree touched (so errors appear), runs the action only when the form isn't invalid, guards against concurrent submits, and exposes progress via form().submitting().

Production tip. Give every form a stable name in its options ({ name: 'profile' }). The forms system uses it to generate name attributes for fields, which matters for form autofill and accessibility.

Anatomy of a Signal Form

Before going deeper, get the five layers of the API straight. Every Signal Form you write is a composition of these pieces:

The vocabulary, asked and answered

APIWhat it isWhy it exists
form(model, schema?, options?) Creates the field tree over a writable model signal. One call per logical form; the model stays the single source of truth.
FieldTree The callable tree that mirrors the model's shape. Typed, reactive navigation of form state without control objects.
Field / field() A node accessor; calling it returns that node's FieldState. Uniform read pattern — same shape at the root, a nested group, or an array item.
FieldState Reactive snapshot: value, errors, touched, dirty, valid, pending… Everything you need to render and react, as signals.
schema() / schema fn Declarative rules bound to paths: validation, disabled, readonly, hidden, debounce, metadata. Behavior lives with the domain shape, not inside components.
[formField] Directive binding a field to a native input or custom control. Bridges the tree to the DOM; replaces CVA for new code.
[formRoot] Directive on a <form> handling submit + novalidate. Turns the native form element into a submission pipeline.

Where does each piece live?

  • Model signal — owned by the component (or a facade) that owns the data.
  • Field tree — created by form(); never constructed by hand.
  • Schema — its own file (*.schema.ts) so it is unit-testable.
  • Directives — used in templates only.
Common mistake. Trying to build the field tree manually (creating "fields" yourself) as with the old preview API. In v22 there is no field() constructor — the tree is derived from the model shape plus schema rules. If you need a field the model doesn't have, change the model (or make it optional/conditional).

The Form Model

What is it?

The form model is the WritableSignal you pass to form(). The field tree does not copy it — it wraps it. Reads and writes pass straight through to the signal.

Why does it exist?

Reactive Forms keep a parallel object graph, which is the root of sync bugs. Signal Forms invert this: your data object is the form's backing store. Loading, editing and saving all operate on one value.

How does it work?

Loading data into the form

Production tip. Keep the model signal and the API DTO types separate. Map between Dto and your Employee model in an explicit mapper — never let API field names leak into the form schema. (More in the API section.)
When to use it: always — every Signal Form has exactly one model signal.
When NOT to use it: don't create multiple signals per field and hand-sync them; that's re-inventing the FieldState. And don't keep a separate "form model" and an "app model" for the same data without an explicit bridge.

Fields & Field Trees

What is it?

A FieldTree is a tree of field accessors whose shape mirrors your model. Primitives become leaf fields; objects become group fields; arrays become array fields you can iterate. It is callable — form() gives you the root's FieldState, form.name() the leaf's.

Why does it exist?

You navigate the tree exactly the way you'd navigate your data object — typed, with no get('address.city') strings and no casts. Nesting is not a special case; a group field behaves like any other field, so sections compose recursively.

How does it work?

Accessing a nested property like p.personal.firstName inside a schema returns a path — a lightweight reference to a location, valid before the form exists. Rules bind to paths; the field tree resolves them at runtime.

When to use it: always — it's the primary way to touch form state.
When NOT to use it: don't keep references to a path outside the schema function and expect live state — paths are structural, not reactive. Use fieldTreeOf(path) or the actual field accessor once the form exists.

Field State

What is it?

Calling a field accessor returns its FieldState: reactive signals for the value and every status flag, plus methods to interact with the field.

Why does it exist?

Rendering a form is 95% reading state — error messages, disabled flags, validity — and FieldState gives you all of it as signals, uniform across leaf fields, groups and array items.

The full surface

How does it work?

Note the subtlety: valid() is true only when there are no errors and no pending validators, while invalid() is true when there are errors regardless of pending work. A field can be simultaneously invalid === false and valid === false while an async check is running. Use pending() for that case.

When to use it: everywhere you read or react to form state — templates, computed values, effects, guards.
When NOT to use it: don't mirror field state into your own signals. If you find yourself writing dirty = signal(false) next to a form, stop — read field().dirty() instead.
Exercise — getError vs errors

Derived State

What is it?

Anything computed from one or more field values: a full name, a counter, a formatted value, a permissions list, a tax bracket. Signal Forms encourage expressing these with computed() over field signals.

Why does it exist?

In Reactive Forms, derived UI state meant subscribing to valueChanges, storing the result in another property, and unsubscribing. Signals make derivation lazy, memoized and glitch-free — the same value can be read by many consumers with one computation.

How does it work?

A chain of derivations is equally natural — salary drives the compensation panel:

When to use it: any value that depends on form input and shouldn't be re-derived imperatively.
When NOT to use it: don't reach for computed() for side effects, and don't compute giant derivations from the whole root value (form().value()) on every keystroke when you only need one field — read the narrowest field that changes.
Production tip. Derived state in a computed() is automatically pure and memoized — perfect for @if guards in templates without extra signals.

Arrays & Repeated Fields

What is it?

Array fields replace FormArray. An array field is iterable and reactive; per-item rules come from applyEach(arrayPath, itemSchema). The structure itself (which items exist) is driven by the model signal.

Why does it exist?

In Reactive Forms, FormArray forced you to mirror every add/remove into the control tree by hand. Here, adding a skill is a plain array update on the model — the field tree follows automatically.

Per-item validation

Rendering and mutating

Production tip. Keep items immutable and keyed. In @for (item of form.skills; track $index), prefer track skill().keyInParent() (the index) when order is the identity — or an id when items can be reordered.
When to use it: any repeated group — skills, line items, contacts, tags.
When NOT to use it: a fixed set of identical fields is not an array; use separate named fields so the schema stays explicit and readable.

Disabled · Readonly · Hidden

What are they?

Three declarative rules that change a field's availability:

  • disabled(path, { when }) — the field cannot be edited and is excluded from the form's value, validation, touched and dirty state.
  • readonly(path, { when }) — not editable, but still submitted and validated (like the native readonly attribute).
  • hidden(path, { when }) — ignored by validation/touched/dirty; you must also remove it from the DOM with @if.

Why do they exist?

Conditional availability was the messiest part of Reactive Forms — disabled logic scattered in subscriptions, race-prone. Declarative when predicates make the intent visible and testable.

How do they work?

Disabled reasons

Common mistake. Forgetting that disabled excludes the value from the submitted model. If you need a field that can't be edited but must be saved, use readonly, not disabled.

Dynamic & Conditional Fields

What is it?

Fields that appear, disappear or change rules based on other fields: an optional address block, a "company vs individual" contact, a contract end date that only exists for contractors. Signal Forms model this with conditional schemas and optional model branches.

Why does it exist?

Reactive Forms handled this with addControl/removeControl plus validator arrays mutated at runtime. Here the rules themselves are conditional, so there is no imperative add/remove choreography.

Conditional sections in the template

Conditional rules with a typed narrowing

applyWhenValue narrows the field's type based on a predicate before applying a schema — perfect for discriminated-union shapes:

When to use it: any field whose existence or rules depend on another field's value.
When NOT to use it: don't hide fields with @if alone and leave their rules running — hidden fields are excluded from validation only if you declare hidden(). Match the template branch with a rule.

Built-in Validation Rules

Validation lives in the schema as rules. Each rule knows when to apply and how to build a ValidationError with a message. Rules skip empty values unless they are the required rule.

Rules are composable and repeatable: you can attach several to one field, and reuse the same rule across forms. To restrict a rule to certain conditions, give it a when predicate:

Options every built-in rule accepts

  • message — the user-facing text (an interpolated string or a function).
  • when — a (ctx) => boolean predicate that gates the rule.
  • Rule-specific parameters — min: (ctx, 18), maxLength: (ctx, 280), etc.
When to use it: any validation expressible with the built-ins — presence, format, range, length, pattern.
When NOT to use it: cross-field, async or domain-specific rules — those need validateTree, validateAsync or validateHttp (next sections).

Custom Validation

What is it?

validate(path, validator) runs your own function against a single field's value. The function returns null when valid, or a ValidationError with kind and message.

Why does it exist?

Business rules rarely fit the built-ins — "rating between 1 and 5 and not equal to your previous rating", "start date within the current fiscal quarter". Custom validators let you encode the rule next to the field and keep a user-facing message in one place.

How does it work?

The validator re-runs automatically whenever the field's value (or any ctx.valueOf dependency) changes. Errors are lazy: computed only when someone reads errors() — great for large forms where you don't validate untouched sections.

When to use it: per-field business rules that depend on the field's own value.
When NOT to use it: rules that depend on other fields — use validateTree; rules that need the server — use validateAsync / validateHttp.

Cross-field Validation

What is it?

Rules that validate relationships between fields. Where do the errors go? You target them explicitly with fieldTreeOf(path), so the error appears under the field the user should fix — not just at the form root.

Why does it exist?

In Reactive Forms, cross-field checks meant reading formGroup.get(...) inside a validator and hoping you remembered to call updateValueAndValidity on every source. Here dependencies are declared, so re-validation is automatic and precise.

How does it work?

Access to the surrounding tree is via the ctx object:

  • ctx.fieldTreeOf(path) — a live field accessor, for reading state and targeting errors.
  • ctx.valueOf(path) — shorthand for the current value.
  • ctx.stateOf(path) — the reactive FieldState.

Attaching it to the group, where it can see both fields:

When to use it: end-date ≥ start-date, password-confirm, "one of the two must be set", discount ≤ price.
When NOT to use it: keep single-field rules on the field itself; don't use validateTree for what validate already covers.

Conditional Validation

What is it?

The same field validated under some conditions and not others: required only for non-EU addresses, length only when a promo code is entered, must-match-pattern only for corporate accounts. Use when on any rule.

Why does it exist?

Conditional validators in Reactive Forms were assembled imperatively — subscribe to a control, re-build the validator array, call setValidators + updateValueAndValidity. Here the condition is declarative and the re-run is automatic when the dependency changes.

How does it work?

Because the when predicate reads ctx.valueOf(p.contractType), the rule re-evaluates whenever that source field changes — no manual triggering.

When to use it: any rule whose applicability depends on other fields.
When NOT to use it: don't gate a rule that is always true — that hides intent. And prefer hidden() + @if for fields that shouldn't exist at all.

Async & Server Validation

What is it?

Two rules for validation that can't be computed locally:

  • validateAsync(path, { debounce, params, factory, onSuccess, onError }) — arbitrary async work (a promise/observable/service call) via a resource.
  • validateHttp(path, { debounce, request, onSuccess, onError }) — HTTP calls with the @angular/common/http HttpResourceRequest.

Why does it exist?

Username/email uniqueness, credit checks, VAT lookups, SSO email verification. These demand debouncing, out-of-order response handling (a slow old response must not clobber a fast new one) and a pending() state the UI can render. The built-in machinery handles all three.

How does validateAsync work?

factory receives the resolved params and must return a resource(). The loader performs the check and returns null (ok) or a ValidationError.

How does validateHttp work?

Reacting to pending state

When to use it: server-side truth checks, uniqueness, enrichment.
When NOT to use it: avoid a server round-trip when the rule is local (it's slow and rate-limited); don't validate every keystroke without a debounce.

API Integration

What is it?

Wiring the form to a real backend: load on init, save on submit, handle loading and saving states, and map between your domain model and the API's DTO.

The three seams

  1. Loading — fetch, map DTO → model, write to the model signal.
  2. Saving — the submission action maps model → DTO and calls the API.
  3. Server errors — map API error codes back to fields.
When to use it: any form backed by a service.
When NOT to use it: don't couple the schema to the API shape; the schema belongs to the model. Keep mappers as pure functions so they are trivially unit-testable.

Nested Forms

What is it?

Because the field tree mirrors the model shape, any nested object is naturally a nested group — no manual nesting API required. A personal object is a group field whose children are personal.firstName etc.

Why does it exist?

Real forms nest: an employee has personal details, employment details, addresses. In Reactive Forms every level meant another FormGroup wired by hand. Here the tree is derived, so nesting costs nothing.

How does it work?

You still control the shape of the data — pick interfaces that match the domain, and the form follows. For deep or wide forms, extract section components (see Reusable Components).

When to use it: any form whose model is more than one level deep — almost always.
When NOT to use it: don't force artificial nesting on flat data; a flat model yields a flat, readable schema.

Dynamic Forms

What is it?

Forms whose structure is not known at compile time: config-driven forms, schema builders, dynamic sections chosen by the user.

Two distinct patterns

1. Data-driven structure (recommended). The model shape is fixed; what varies is which branches are present and how many items an array has. Conditional schemas (applyWhen, applyWhenValue) + arrays cover this with full typing.

2. Metadata-driven rendering (last resort). A configuration describes fields and the template renders them generically. This is powerful but sacrifices type-safety and readability — you trade the compiler for indirection.

When to use it: data-driven structure for "same form, different branch" needs.
When NOT to use it: don't build a metadata-driven form engine for a fixed form — it's over-engineering and harder to maintain than the direct schema.

Reusable Field Components

What is it?

Custom controls that work with [formField]: a styled text input, a select, a toggle, a date picker. The contract is tiny — implement FormValueControl (or FormCheckboxControl) and the directive drives it. No ControlValueAccessor required for new code.

What about existing CVA-based controls?

[formField] resolves bindings in priority order: native element → custom control (FormValueControl) → ControlValueAccessor. So third party CVA components keep working, but your own controls should use the modern contract.

When to use it: any repeated control UI — inputs, selects, toggles, pickers, chips.
When NOT to use it: don't wrap a native input in a component with no extra behavior; a raw [formField] input is already fine.

Component Architecture

What is it?

Where the model signal lives, who creates the field tree, and how section components get their fields. The rules of thumb:

  • One owner. The component that owns the model signal also owns form() and the schema.
  • Pass fields down, not models. Sections receive the exact field accessors they need (a group field), keeping their inputs narrow and testable.
  • Emit semantic events up. Sections emit things like addSkill, never raw form state mutations — the parent owns mutations.
  • Schema in its own file. *.schema.ts, unit-testable in isolation.
When to use it: every form bigger than one screen, and any form with more than ~6 fields.
When NOT to use it: tiny inline forms can stay in one component — splitting adds ceremony with no benefit.

RxJS Integration

What is it?

Signal Forms are signals, not streams — but real apps already use RxJS (websockets, route params, API libraries, NgRx). Integration means translating between the two worlds deliberately, not calling toSignal on everything.

Why does it exist?

You can't subscribe inside a computed(), and you shouldn't sprinkle subscriptions across components. A small, explicit bridge — one source of truth — beats ad-hoc wiring.

State Management

What is it?

Where form state sits relative to app state. Signal Forms work great standalone; they also coexist with NgRx and other stores. The question is who owns what.

The split that works

  • Store owns: entity data, auth, global loading/error, "which item is being edited".
  • Form owns: the editing draft, per-field validity, touched/dirty, pending.
  • The boundary: load from the store into the model signal on init; write the model signal back to the store on a deliberate action (Save).

Feeding the store from the form (only when it matters):

When to use it: apps with a store, or forms that must share drafts across routes.
When NOT to use it: don't dispatch per keystroke — the store doesn't need every intermediate edit; save on submit or on a debounced "persist draft".

Accessibility

What is it?

Signal Forms don't auto-fix accessibility — they give you the signals to wire it correctly. The essentials:

  • aria-invalid from the same errors() you render.
  • aria-describedby pointing at the visible message.
  • Labels tied to controls; errors announced when they appear.
  • Focus management on validation failure and dynamic sections.

Testing

What is it?

Three levels: pure unit tests of schemas and mappers (no Angular needed), component tests of fields + templates, and E2E flows for the critical journeys.

  • Add a transferDate to the model that appears (and is required) only when department differs from the loaded employee's original department.
  • Add an async check that email is not used by any employee besides the current one.
Show solution

Use hidden(p.transferDate, { when: (ctx) => ctx.valueOf(p.department) === originalDepartment }) plus required(p.transferDate, { when: … }) mirroring the condition; and a validateHttp/validateAsync rule on p.email that queries the API excluding the current employeeId. Keep the original department in a read-only field of the model so the schema stays pure.

Learning Path & Next Steps

If you made it here, you can build production Signal Forms. A suggested order to apply it:

  1. Rebuild one small form you already own (profile, settings) with form() + [formField].
  2. Add real validation — move every validator into a *.schema.ts file.
  3. Split a monolith into presentational section components receiving field inputs.
  4. Add one cross-field rule and one async rule with validateTree / validateAsync.
  5. Build a reusable control with FormValueControl and reuse it in two places.
  6. Test the schema in isolation and the binding in a component test.
  7. Migrate one real form end-to-end using the Migration section.

Deep-dive ideas

  • Dynamic schema builders (applyWhen, applyWhenValue) for config-driven workflows.
  • validateHttp vs a shared httpResource for cacheable lookups.
  • Multi-step wizard: one model signal + step sections + per-step schema rules.
  • WebMCP tool registration (provideExperimentalWebMcpForms — experimental, label it).
  • Performance profiling of a 500-field form with the DevTools profiler.
Final exercise — combine everything

Build a small "Project" form: title (required, 3–80 chars), owner (required select), a budget optional number that becomes required when funded is toggled, an async check that the title is unique, and a tasks array (applyEach with name + estimate). Wire a mock save that returns a server error on a specific task. That is the full signal-form toolbox.

Show solution sketch

Compose: required(p.title, { minLength: … }) + validateAsync(p.title, …) for uniqueness; conditional required(p.budget, { when: (ctx) => ctx.valueOf(p.funded) }); applyEach(p.tasks, taskSchema); and a submission.action that returns a fieldTree-targeted error against p.tasks[index].name.
